# سامانه درخواست خرید پادرا

نسخه مستقل سامانه درخواست خرید شرکت پادرا؛ طراحی‌شده با Flask، SQL Server، Waitress، Flask-Login و رابط فارسی RTL. پورت پیش‌فرض اجرا 3942 است.

## قابلیت‌های نسخه اول
- ورود با همان جدول کاربران سازمانی `[Project].[loginusers]` در دیتابیس `bi` و SQL Server Authentication.
- کنترل دسترسی متمرکز با خواندن مستقیم جداول `Project.IAM_*` در دیتابیس مشترک؛ بدون API، توکن یا SSO مبتنی بر توکن.
- نقش‌ها و مجوزهای برنامه در مخزن `serkan-iam` مدیریت می‌شوند؛ گردش تأیید و تعیین تأییدکننده هر درخواست در جداول عملیاتی همین برنامه باقی می‌ماند.
- اتصال جداگانه دیتابیس احراز هویت و دیتابیس درخواست‌های خرید از طریق متغیرهای محیطی.
- ثبت درخواست خرید با اطلاعات سربرگ، نوع اقلام، محل تأمین، واحد درخواست‌کننده و دارایی ثابت.
- جدول پویای اقلام: افزودن/حذف ردیف، کد و شرح کالا، واحد، مقدار، تاریخ نیاز و محل مصرف.
- شماره درخواست و تاریخ شمسی خودکار.
- گردش تأیید مرحله‌ای قابل پیکربندی در جدول `Project.approval_routes`.
- ثبت تاریخچه عملیات و قابلیت چاپ A4.
- محافظت CSRF و استفاده از پارامترهای SQL.

## راه‌اندازی
1. Python 3.11+ و ODBC Driver 17 یا 18 نصب باشد.
2. فایل `sql/create_purchase_request_schema.sql` را در دیتابیس `bi` اجرا کنید.
3. در مخزن `serkan-iam` ابتدا `sql/001_create_iam_schema.sql` و سپس `sql/002_seed_padra_purchase_permissions.sql` را در دیتابیس `bi` اجرا کنید.
4. یک محیط مجازی بسازید و وابستگی‌ها را نصب کنید:
   `python -m venv .venv`
   `.venv\\Scripts\\activate`
   `pip install -r requirements-windows.txt`
5. از `.env.example` یک فایل `.env` بسازید و `FLASK_SECRET_KEY` را با مقدار تصادفی قوی پر کنید. `AUTH_DB_*` باید به دیتابیس `bi` و جداول کاربران و IAM متصل شود؛ `DATA_DB_*` به دیتابیس گردش خرید متصل شود. هر دو می‌توانند به همان دیتابیس `bi` اشاره کنند. هرگز فایل `.env` را در Git ثبت نکنید.
6. اجرای استاندارد ویندوز: فایل `run.bat` را اجرا کنید. اجرای دستی: `python -m waitress --listen=0.0.0.0:3942 --threads=8 app:app`
7. بررسی سلامت سرویس: `http://SERVER:3942/healthz` (باید JSON با status=ok برگرداند).
8. آدرس برنامه: `http://SERVER:3942`

## مجوزهای SQL
- دیتابیس احراز هویت: دسترسی SELECT به `[Project].[loginusers]`.
- دیتابیس درخواست خرید: دسترسی SELECT/INSERT/UPDATE به جداول schema `Project`.
- حساب برنامه نباید دسترسی DDL داشته باشد؛ اسکریپت ساخت جداول را مدیر دیتابیس اجرا کند.

## تنظیم گردش تأیید
پس از ساخت schema، برای هر نوع درخواست و هر مرحله یک ردیف در `Project.approval_routes` اضافه کنید. مقدار `request_type` یکی از `goods`، `service`، `equipment` یا `other` است. `approver_username` باید دقیقاً با نام کاربری جدول سازمانی مطابقت داشته باشد. ترتیب مراحل با `step_no` مشخص می‌شود.

نمونه:
```sql
INSERT INTO Project.approval_routes(request_type, step_no, approver_username, approver_title, is_active)
VALUES ('goods', 1, N'username1', N'مدیر واحد', 1),
       ('goods', 2, N'username2', N'مدیر بازرگانی', 1);
```


## مدیریت دسترسی با Serkan IAM

1. سرویس IAM را روی پورت 3943 اجرا و وارد پنل آن شوید.
2. در بخش «پروژه‌ها» وجود پروژه `padra-purchase-request` را بررسی کنید.
3. نقش‌ها و مجوزها را در بخش‌های «نقش‌ها» و «دسترسی‌های نقش» تنظیم کنید.
4. از بخش «تخصیص نقش» نقش را به کاربر بدهید؛ تاریخ شروع و پایان اختیاری است. برای لغو دسترسی از «لغو نقش» استفاده کنید.
5. برنامه خرید در هر عملیات مجاز، مستقیماً از SQL Server وضعیت نقش و مجوز کاربر را می‌خواند. قطع یا حذف تخصیص در IAM در بررسی بعدی اثر می‌گذارد.
6. فهرست کارشناسان قابل تخصیص نیز از کاربران دارای نقش `serkan_purchase_specialist` در IAM خوانده می‌شود؛ برای اضافه‌کردن کارشناس جدید، فقط حساب سازمانی موجود را در IAM به این نقش منتسب کنید.

### مجوزهای مصرف‌شده توسط برنامه

| مجوز | کاربرد |
|---|---|
| `requests.create` | ثبت درخواست جدید |
| `requests.view_all` | مشاهده همه درخواست‌ها |
| `requests.approve.step1` | تأیید مرحله مدیرعامل پادرا |
| `requests.approve.step2` | تأیید مرحله مدیر خرید سرکان |
| `requests.approve.step3` | تأیید مرحله کارشناس خرید |
| `requests.assign_specialist` | تخصیص کارشناس |
| `requests.reassign_specialist` | تغییر کارشناس |
| `requests.export` | خروجی CSV |

کاربر برای مشاهده درخواست باید درخواست‌دهنده، یکی از تأییدکنندگان آن درخواست، یا دارای مجوز `requests.view_all` باشد. داشتن نقش مدیر IAM به‌تنهایی مجوز تأیید درخواست خرید ایجاد نمی‌کند.

## نکات نسخه اول
- ساختار دقیق کدینگ کالا، واحدهای سازمانی، فهرست تأمین‌کنندگان و امضای دیجیتال هنوز از دیتابیس ERP دریافت نشده است؛ بنابراین ورودی‌های مرتبط فعلاً قابل ورود دستی هستند.
- امضای تصویری داخل فرم مرجع در نسخه اول به‌صورت جایگاه تأیید و مشخصات تأییدکننده نمایش داده می‌شود؛ امضای دیجیتال واقعی نیازمند سیاست و منبع امضای سازمانی است.
- برای بهره‌برداری واقعی، حساب‌های SQL را با حداقل دسترسی بسازید و رمزهای دیتابیس را فقط در Environment Variables نگه دارید.
